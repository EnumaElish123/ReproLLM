# 0.2.0 release notes — draft

**Not released.** M4's implementation and available metadata validation are
complete, but its manual Linux H2 check remains pending. On 2026-09-19 the
maintainer requested pushing verified code first. The main package version
remains `0.1.1`; no `v0.2.0` tag or publication is claimed by this document.

## Proposed release notes

ReproLLM 0.2.0 adds `reprollm lock` and Level 2 audits. The manifest describes
the experiment's intent; the lock records resolved model/tokenizer/dataset
revisions, configuration and prompt hashes, backend versions and environment
metadata, together with each value's source and confidence.

This is the **first release of the lock schema v1 writer**
(`reprollm.lock`, `schema_version: 1`). Manifest schema v1 remains compatible.
There is no migration from an earlier supported lock writer. Schema exports
are unchanged from the previously published schema definitions.

- Resolve Hugging Face metadata directly over bounded HTTP without installing
  `huggingface_hub`, downloading weights or downloading dataset contents.
- Use `lock --offline` for local hashes and explicitly declared or unresolved
  remote revisions. Use `lock --check` to detect stale manifest/project rules
  without making network requests or writing files.
- Check nine lock-level rules plus lock freshness and working-tree file hashes.
  API snapshot aliases retain their limited pinnability; unresolved metadata
  retains its failure source.
- Share the HF client's mirror, retry and sanitized-error behavior with
  `doctor --check-network`. Accept supported Apple Git vendor version strings.
- Keep four runtime consistency rules explicitly pending for M5, following the
  maintainer-approved clarification in Issue #2.

### A real API judge lock

This fragment comes from the Project B FastChat metadata validation on
2026-09-19. No API inference or provider-verification call was made.

```yaml
models:
  judge:
    provider: openai
    id: gpt-4o-2024-08-06
    pinnability: snapshot_alias
    revision:
      value: null
      source: provider_no_pinning
      confidence: unresolved
      resolved_at: null
      note: null
    observed_at: '2026-09-19T09:33:28Z'
    tokenizer: null
    chat_template: null
    config_sha256: null
    adapter: null
    local: null
    dtype: null
    quantization: null
    trust_remote_code: null
```

The dated identifier is recorded as a provider snapshot alias. ReproLLM does
not invent an exact provider revision or promise immutable API behavior.
This model produces INFO for `model.revision_pinned`, while judge pinnability
and the repository's judge-prompt hash checks pass.

### Validation and limits

The local quality gate passed 728 tests with 94.87% coverage, plus lint,
formatting, strict typing, schema and generated-documentation checks.
Three reviewed fixture snapshots cover exact HF metadata, unavailable backend
versions, API aliases and gated metadata failures. All five pinned external
repositories pass the unchanged Level 0 gold and the available M4 metadata
scenarios. See the [full validation record](../dogfooding/m4-lock.md).

Project C's public repo metadata resolves exactly, but gated files return
401 anonymously and 403 with the provisioned credential because the model
author rejected access. Both denial paths are recorded without credential
leakage; successful restricted-file access is not claimed. Minimal model
execution, runtime consistency and dataset content fingerprinting are outside
this release's scope.

## Packaging preflight and remaining release steps

A disposable copy of the source was assigned `0.2.0` solely for packaging
preflight. Both sdist and wheel built successfully, and the wheel was
installed into a separate environment. Installed-package version, lock help,
the bundled core profile and schema export passed; exported schemas match
the repository. No heavy dependency was installed. The actual source version,
lockfile and release tags were unchanged.

Preflight artifacts and their hashes are retained outside the repository
under `../dogfooding/m4-lock-2026-09-19/release-preflight/`. They are validation
artifacts, not final release distributions; rebuild from the final release
commit after its gates pass.

Before publishing:

1. Complete the M4 H2 Project A online lock check on a provisioned Linux

2. Record its sanitized lock and outcomes, and rerun the applicable release
   quality and validation gates.
3. Set the package and project lock version to `0.2.0`, move the final changes
   and judge fragment into a dated CHANGELOG release section, and verify CI.
4. Create and push `v0.2.0`; verify the existing trusted-publishing workflow
   and the resulting PyPI and GitHub release artifacts.
